# Summary: 2026-10-09

## Repository
- pnpm workspace with `packages/engine` (pure game logic) and `packages/content` (tuning constants).
- Strict TypeScript, Vitest, ESLint, and a GitHub Actions workflow. `CLAUDE.md` holds the project rules and `SPEC.md` the build spec.
- Lint enforces engine purity: no `Math.random`, no `Date.now`, no imports from other packages or `node:*`.

## Engine
- **MurmurHash3 (32-bit)**, written in the repo and checked against 13 published vectors.
- **Enhanced double hashing** derives k positions from two hashes: `h1 + i·h2 + (i³ − i)/6 (mod m)`. The plain form `h1 + i·h2` clumps positions and inflated Bloom false-positive rates by up to about 4x at small `m` or large `k`.
- **Seeded random numbers** (sfc32). Named sub-streams derive from the seed and name alone, so drawing from one never shifts another. State round-trips through JSON.
- **Stats helpers:** normal quantile (`zForConfidence`), binomial upper bound, exact Clopper-Pearson interval, `clamp`.

## Structures
Each takes a Space budget in bits, derives its own parameters, and answers with an estimate plus low and high bounds.

| Structure | Answers | Behavior |
| --- | --- | --- |
| Exact Memory | All | Exact until full (64 bits per distinct value), then refuses new values and widens its bounds by the number refused. Handles deletes. |
| Reservoir Sampling | All, roughly | Uniform sample, estimates scaled by sample fraction, exact Clopper-Pearson bounds on frequency. Cannot see deletes, so deleted values stay as ghosts. |
| Bloom Filter | Presence | No false negatives. False-positive rate follows `(1 − e^(−kn/m))^k`. Ignores deletes. |
| Count-Min Sketch | Frequency | Never underestimates a live value. Reports confidence `1 − e^(−depth)`. Each row hashes with its own seed so rows collide independently. Supports deletes. |
| LogLog | Count | Error about 1.30/√m, biased on small streams. Ignores deletes. |
| Linear Counting | Count | Estimate `−m·ln(V)`. When no zero bits remain, the upper bound is infinite. Ignores deletes. |

Bloom, Count-Min and LogLog also merge with a same-shaped, same-seeded instance.

## Tests
- Every structure has unit tests and a 1,000-trial seeded statistical test against its theoretical error.
- The Bloom test covers five size configurations and fails on plain double hashing.
- Reservoir frequency coverage is tested at 98%, 80%, 1% and 0.2% shares. Count-Min has a row-independence test (all-row collision rate 1/w^d).
- 123 tests pass; lint is clean. A test checks the engine's stand-in constants match `balance.json`.

## Content package
- `balance.json` holds the spec's tuning constants (including Count-Min's default depth and LogLog's error coefficient) at placeholder values, validated by a Zod schema that rejects missing, extra or out-of-range keys.
- The engine receives only the two constants it needs (bits per stored value, default confidence) as a constructor argument.

## Known limitations
- Bloom at `m = 8192`, `k = 14` has a false-positive rate about 14% above the textbook rate; the cause is not understood.
- LogLog reports 95% bounds even on streams too small for its error law to hold.
- Linear Counting's infinite upper bound has no JSON encoding yet.
- Structures hold typed arrays and Maps, so they have no JSON snapshot form yet.
- The Frequency challenge shape is decided (the enemy names the value, per `SPEC.md`) but not implemented yet.
- Count-Min and Reservoir distinct-count bounds are loose by design, so their coverage tests pass with maximum margin and would not catch a small slip. LogLog, Linear Counting and Bloom land within a few percent of theory.
