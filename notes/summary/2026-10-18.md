# 2026-10-18

- **The browser check of the web version is done.** The heatmap, register bars and the other structure views look right. One bug turned up (a small strip only filled part of its width) and is fixed. A run played to its end in the real page offers the replay download.
- **Milestone 7 (the exporter) has started with the sizing step.** Given a real workload (how many items, how many different ones, how much error is acceptable, how much memory there is) it now works out the size of each structure: for example, a Bloom Filter for 1,000 items at 1% false positives needs about 9,600 bits and 7 hashes. Each size is checked against the game's own structures over hundreds of random streams, and the check caught that a first formula landed slightly over the target. Still to come: the written reports, the TypeScript and Python code templates, the zip file, and a CI job that tests the generated code in both languages.

- **The toolkit code is written in both languages, and tested.** There are now TypeScript and Python versions of every structure (Exact Memory, Reservoir Sampling, Bloom Filter, Count-Min Sketch, LogLog, Linear Counting and HyperLogLog), a hashing file, a sizing calculator and their tests: 17 in each language, including statistical checks that each structure stays within its stated error. Both languages are also checked against the same "known answers" produced by the game's own structures, so the exported code behaves exactly like the game's. `pnpm export check` builds both toolkits and runs them; breaking the code on purpose in 14 ways was caught every time. A new CI job runs this on Python 3.9 and 3.13, but it has not run on the server yet. Still to come: the written reports (README, SIZING, FIELD_REPORT), the zip file and an export screen in the browser.

- **The export now produces a real zip.** `pnpm export toolkit python replays/prober-3-won.json out.zip --items 2000000 --distinct 80000 --error 0.02` checks a recorded run and writes a zip with the code and tests for every structure used in the run, a sizing calculator, and three written reports. `SIZING.md` says how big each structure should be for your real workload (for example a Bloom Filter for 2 million items at 2% needs about 1.9 MiB and 6 hashes, with the exact constructor call), and says plainly what it still needs if a number was left blank. `FIELD_REPORT.md` tells the story of the run: each fight, which structures were deployed, how the strikes went and the mistakes (a count estimate 80% off, a strike that was too weak). `README.md` says when each structure is the right tool. It also shows how tightly you ran each structure in the game compared with what production would use (the game's Space is deliberately tight). Left to do: a button for this in the browser, and the first CI run.

- **The browser can now export the toolkit.** When a run ends, an "Export toolkit" button opens a small form (language, how many items, how many different ones, acceptable error, memory budget; any can be blank) and builds the zip right in the page, with no server. Checked in the browser at desktop and phone widths: the zip it made held the three reports, the Python code for the structure used, the sizing calculator and the known answers; bad input (such as an error of 150%) shows a clear message. Milestone 7 is now complete except for the first CI run and a CI step that tests a zip built from a real run.

- **Milestone 8 is done: a learned player beats the Greedy bot.** A learning program now plays the whole game (fights, rewards, rest stops), choosing from 218 moves with only legal ones offered. After about 20 minutes of training it wins 93% of 200 runs it has never seen (186 wins), against 54% for the Greedy bot on the same runs; on a second set of 200 different runs it wins 93% again against Greedy's 48.5%. Every one of its finished games was saved as a replay and checked by the game's own verifier: all 374 are genuine. Getting there took four crashes and one real problem: at first it learned to stall until the step limit, because running out of steps cost nothing; now running out counts as a lost run. The crashes turned out to be a too-strict numeric check in the learning library, not a bug in the game. Left out: one training run only, no comparison with the Oracle on speed, and the trained model is not saved in the repository.

- **Milestone 9 has started with two new Frequency structures: Count Sketch and the Top-K Tracker.** Count Sketch counts with plus and minus signs so that collisions cancel instead of piling up: its answers are not biased high or low, but half the time they are a little low, which a strike punishes, so it is a structure for players who read its upper bound. The Top-K Tracker is made by fusing Count-Min with Exact Memory at a rest stop: it follows the heaviest values exactly and the rest roughly. Measured, the Top-K Tracker nearly matches Exact Memory on moderately skewed streams (damage 14.4 against Count-Min's 8.6 on the big streams), and answers its five heaviest values with a quarter of Count-Min's error. What it does not fix: on streams with no favorite values the true counts are so small that every structure is swamped by noise, so that part of the "Frequency gap" is a property of the question, not of the structures. The bots' whole-run win rates are unchanged within noise (Greedy 44% against about 46%). The learned player from Milestone 8 no longer fits the bigger game and would have to be retrained. Next in this milestone: Cuckoo Filter and KMV, then the new challenge kinds (Likeness, Rank) and the Cunning enemy.

- **A player can no longer stall a fight for ever.** The learned player's 26 stuck games were all the same thing: after beating up to six enemies it repeated "place a structure, take it away" on one slot, which costs nothing and changes nothing, so it never moved the fight on. In all 26 it began between its 23rd and 79th move and ran until the step limit; 24 of the 26 were in the Elite or Boss fight. The game now limits the free changes: two per slot each turn (placing or removing both count), and six enchantment moves at a rest stop. After that the only way forward is to end the turn. A test tries every kind of stalling, and arbitrary junk, and always sees the fight end within its turn limit. The bots are not affected (their win rates are unchanged). The five saved replays were re-recorded for the new rules. The learned player would have to be retrained for the bigger game.

- **Two more Phase 2 structures: the Cuckoo Filter and K-Minimum Values.** The Cuckoo Filter answers "have I seen this?" like a Bloom Filter but can forget deleted values. Measured, it wins clearly when the enemy deletes things (damage 30.7 against 18.6 on Minions with Medium Churn), and loses on big calm streams, because once it is full it starts dropping fingerprints and hides real values (18.3 against 27.9 on Elites with no Churn). K-Minimum Values counts distinct values from the smallest hashes: exact up to 256 values, about 6% error beyond. It does not beat Linear Counting at today's stream sizes; its use is merging counts across streams, which needs multi-enemy fights. The bots prefer the Cuckoo Filter when there is Churn and they own one; having them go and pick it up as a reward made them win 4 points less often, so they do not. I also found and fixed the cause of a test that had failed once in a while since the export work: the zip file stamped its folders with the current time.

- **The Rank challenge exists (milestone 9, step 3a).** A Rank enemy puts armor at a position in its stream's values (for example the 90th percent mark): you strike with a value, a value that ranks below the armor is blocked, and one far above it wastes the strike, so the best strike is the value just at the armor. Exact Memory answers it exactly while its table has room, and Reservoir Sampling answers it with an honest range. Reading the tests turned up a flaw: when one value is very common, no value sits close enough to the armor and even a perfect player deals no damage, so the armor now snaps to a rank a value can actually reach. Rank enemies are written but switched off: turning them on cut the Greedy bot's win rate from 44% to 26%, because the two structures that can answer Rank today are too blunt. They go live once the KLL and t-digest structures (the next step) exist and the balance is tuned. The bots, parser, narration, query screen and the learning environment all understand Rank.

- **Two quantile structures for Rank: the KLL Sketch and the t-digest.** Both estimate where a value ranks in the stream within a couple of percent, in a few thousand bits. The KLL Sketch is equally accurate at every position; the t-digest is sharpest at the extremes (the 99th percentile), which is what the hardest enemies ask for. Both are far sharper than Reservoir Sampling at the same size. Their error figures were measured by simulation, and breaking the code on purpose was caught in 16 of 17 ways; the one that slipped through changes a value that cannot be observed. Rank enemies are still switched off until the balance is re-tuned.

- **Rank enemies are now in the game.** About one enemy in six or seven asks the Rank question. With them on, the Greedy bot wins 37% of runs instead of 44% and the Prober 21% instead of 26%; a stronger setting (28% for Greedy) was too harsh because the starting kit cannot answer Rank and the bots only get the new structures as rewards. The new structures are now in the bots' reward taste.

- **The Likeness challenge and MinHash are in.** A Likeness enemy holds up six sets of values; a set is real if at least 60% of the values in it or in the enemy's stream are shared. You strike the real ones (same rewards and penalties as Presence). MinHash compares sets by keeping the smallest hash per hash function, and tells you which sets it thinks are real and how many of those it is sure about; Exact Memory can also do it but only while its table holds the whole stream. A new enemy trait, Likeness, decides how close the look-alikes are to real (far, near, or just under the line). Starting kits cannot answer Likeness, so the weight is small: Greedy wins 36% of runs (about 40% without it) and the Oracle still wins every run. Churn hurts MinHash: with heavy deleting it misses most real sets (it was tested honestly and a "fix" that did not help was dropped).
