## Design decisions
These are choices the spec left open.

| Topic | Decision |
| --- | --- |
| Tuning constants | Passed to structures as `StructureConstants { valueBits, confidence }`, built by `structureConstants()`, because the engine cannot import `content`. |
| Random sub-streams | `rng.split(name)` derives from the seed and name, not the draw position, so streams never shift each other. Stream names are part of the replay format. |
| Frequency challenge | The enemy names the heaviest live value `v`. The player queries it and never sees the true count `f`. Ties go to the lowest value. |
| Presence answers | `estimate` is the list of flagged targets. `low`/`high` bound how many of them are real. |
| Bloom sizing | With no expected item count, assume 10 bits per item. The error bound uses the actual fill, not the planned load. |
| Count-Min | Default depth 4. Confidence is `1 − e^(−depth)`, not 0.95. `high` equals the estimate. Deletes stop at zero. |
| LogLog | Register count is the largest power of two with `5m ≤ Space` (minimum 16). Small streams are biased on purpose. Bounds are lopsided (lognormal). |
| Linear Counting | When no zero bits remain, `high` is `Infinity`. This has no JSON encoding yet. |
| Reservoir Sampling | Distinct count uses the GEE estimator. Frequency uses the exact Clopper-Pearson interval. Presence has `low = flagged`, `high = all targets`. |
| Exact Memory | Counts refused inserts and widens `high` by that amount. |
| Merging | Bloom (OR), Count-Min (add) and LogLog (max) merge. Merging refuses a mismatched shape or seed. |
| Hashing | Bloom uses enhanced double hashing (`h1 + i·h2 + (i³ − i)/6`). Count-Min rows each use their own seeded hash. |

## Problems found and fixed

**1. Bloom false positives (hashing).** Plain double hashing, the spec's formula, ran 10% over theory at `m=2048, k=7` and 3.6 to 3.9x over at `k=14`. Positions clumped together. Enhanced double hashing brings it within 3% in four of five test configurations. The fifth (`m=8192, k=14`) is still 14% high, which is unexplained. The Bloom test now covers five configurations and fails on plain hashing.

**2. LogLog bounds.** A symmetric range covered the truth 92.4% of the time at 64 registers (target 95%). Lopsided (lognormal) bounds fixed it.

**3. Reservoir frequency bounds.** The normal approximation covered 70.9% of the time at a 98% share, and returned a zero-width range when every sample matched. A Wilson interval still failed at a 0.2% share (87.4%). The exact Clopper-Pearson interval fixed it.

**4. Count-Min rows.** Rows derived from double hashing collided together about 7 times too often (about 6,060 all-row collisions against 875 expected). Each row now has its own seed. Consequence for Cunning: colliding with a value in every row now takes about `w^d` candidates (2.7e8 at width 128, depth 4), far above the 50,000-candidate search budget, so that attack needs partial-row collisions or small widths.

Lesson: judge statistical tests by their observed numbers, not by a tolerance picked by feel.

## Statistical tests
Each structure runs 1,000 seeded trials.
- **Coverage:** the true answer must land inside the reported range at least the stated confidence minus three standard deviations of chance (`coverageFloor`).
- **Bloom:** zero false negatives, and a false-positive rate near theory in five configurations.
- **Count-Min:** zero underestimates, overshoot within the band at rate `e^(−depth)`, and rows collide independently.
- **LogLog and Linear Counting:** RMS error within 10% of theory, plus coverage.
- **Reservoir:** uniform sampling, unbiased frequency scaling, coverage at four shares (98%, 80%, 1%, 0.2%) and for distinct counts.
- **Exact Memory:** no error while under capacity, including with deletes.
- Never loosen a bound to make a test pass; fix the structure instead.

### Measured error against theory
Numbers from 1,000 seeded trials per row (the coverage floor is about 0.929 for a 95% claim).

| Structure and setup | Measured | Reading |
| --- | --- | --- |
| LogLog, 256 registers, 20,000 values | RMS error 0.97x theory, coverage 0.957 | Tight |
| LogLog, 64 registers, 8,000 values | RMS 1.00x theory, coverage 0.953 | Tight |
| Linear Counting, load 0.24 / 0.98 / 1.95 | RMS 1.00x / 0.98x / 1.01x theory, coverage 0.955 / 0.950 / 0.945 | Tight |
| Bloom, five configurations | Within 3% of theory except `m=8192, k=14` (+14%) | Tight, one gap |
| Count-Min, width 128, depth 4 | 0 underestimates, 0 overshoots past the band, coverage 1.000 | Loose by design |
| Reservoir distinct count | Coverage 1.000 | Loose by design |
| Reservoir frequency, 80% / 20% share | Coverage 0.959 / 0.959 | Close to nominal |
| Reservoir frequency, 98% / 1% / 0.2% share | Coverage 0.992 / 0.996 / 0.994 | Conservative at the extremes |
| Bloom real-target count | Coverage 1.000 | Conservative |

Reading the table:
- **Tight rows** are the ones where a regression would show up as a failing test.
- **Loose rows** pass with the maximum margin. Count-Min's bound comes from a worst-case argument (Markov's inequality) and is far looser than its real behavior, and the GEE ratio bound for distinct counts is similarly wide. These tests catch gross failures such as underestimates, but would not notice the guarantee slipping from 98% to 95%. The Count-Min row-independence test covers the one subtle failure found so far.
- Reservoir's mean estimate matched the truth within chance at every share, so there is no bias.
