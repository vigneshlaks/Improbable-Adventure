## Design decisions made (not dictated by spec; revisit if wrong)
1. **Constants injection.** Engine cannot import content, so `StructureConstants {valueBits, confidence}` is passed to every structure constructor. `content.structureConstants()` builds it from balance.json. `testUtils.TEST_CONSTANTS` mirrors it for engine tests.
2. **Rng.split(name)** derives from the parent's *seedKey string*, not its position, so sub-streams never shift when siblings are drawn from (spec determinism rule).
3. **Frequency challenge shape**: `{kind:"frequency", value}`. A sketch cannot find the most frequent value itself, so the engine/challenge must supply the shielded value. This is an M2 question: confirm the enemy reveals the value (or a candidate list) at challenge time. Spec is silent.
4. **Presence answers** are `estimate: number[]` (flagged targets). `low/high` bound the *count of real targets among the targets*: Bloom `low = flagged - binomialUpper(T, fillFpr)`, `high = flagged`. Reservoir/Exact define their own (see code comments).
5. **Bloom default knob**: if no expected-items knob, assume 10 bits/item (`DEFAULT_BITS_PER_ITEM`). Bound uses fill-based FPR `(fill)^k`, not the textbook formula, so duplicates/overload are reflected.
6. **CMS**: default depth 4; reports `confidence = 1 - e^-d` (not 0.95) because that is the actual guarantee. `low = est - (e/w)*N`, `high = est`. Deletes clamp at 0.
7. **LogLog**: m = largest power of two with 5m <= Space (leftover bits unused; `spaceBits()` reports 5m). Min 16 registers. alpha_m = 0.39701 - (2pi^2 + ln^2 2)/(48m). Small streams are badly biased on purpose (empty counter estimates ~0.4m). Tests use n >> m.
8. **LogLog bounds are lognormal, not symmetric.** First version used est*(1 +- z*sigma) and **undercovered at m=64 (92.4% vs 95%)**. Fixed the *structure* (invert lognormal quantiles, sigma_ln = sqrt(ln(1+sigma^2))), did NOT touch the test. RMS and bias tests were fine throughout.
9. **Linear Counting saturated** returns `high: Infinity`. Infinity is not JSON-safe; fine for answers held in memory, but if answers/events get serialized in M2 (replay logs), pick an encoding (e.g. null or a sentinel) first.
10. **Reservoir** distinct-count uses GEE estimator with ratio bounds sqrt(N/n); frequency uses normal approximation with finite-population correction, and a "rule of three" style upper bound when the sample has zero hits. Presence: `low = flagged` (assumes no ghosts, which the structure cannot know), `high = all targets`.
11. **ExactMemory** tracks `refusedInserts` and widens `high` by it (it only knows a count of dropped inserts, not which values).
12. Structures expose `merge()` where the spec lists them mergeable and they exist in M1 (Bloom, CMS, LogLog). Merge refuses mismatched shape or seed.

## Double hashing fix (later the same day)
Measurement showed the Bloom FPR test was hiding a real defect: **plain Kirsch-Mitzenmacher double hashing** (the spec's formula) was +10% (m=2048,k=7) and +290% to +390% (k=14, m=8192 or 8000) over the textbook rate, and also worse than `fill^k` (so correlated positions, not noise or a hash bug). Absolute excess was ~1.5/m regardless of k, consistent with degenerate steps (h2 sharing a factor with m) collapsing the progression.
- **Fix:** `nthHash` now uses enhanced double hashing, `h_i = h1 + i*h2 + (i^3 - i)/6`. SPEC.md tech-stack row updated to match (original spec file untouched).
- **Result (obs / textbook):** m=8192,k=7 1.00; m=2048,k=7 1.00; m=5000,k=5 1.01; m=8000,k=14 1.03; **m=8192,k=14 1.14 (~3.5 sigma, residual not explained; power-of-two m + high k)**.
- **Test rewritten:** 5 configs (small m, non-power-of-two m, k=14). Tolerance = 4 Poisson sigma of expected FP count + 3% of theory (not a flat 8%). Verified it FAILS on plain double hashing (3 of 5 configs).
- Unverified: whether degeneracy is the whole cause of the original excess (odd-h2-only variant cut k=14 from 3.9x to ~2.2x, so partly). Also did not check Count-Min specifically for the same degenerate-row issue; its tests still pass with enhanced hashing.
- Lesson: judge statistical tests by printing observed numbers; do not pick tolerance by feel.

## Statistical tests (per spec: 1,000 seeded trials each)
- Coverage floor = nominal confidence minus 3 binomial sigma over the trials (`coverageFloor`).
- Bloom: zero false negatives; observed FPR within +-8% of `(1-e^(-kn/m))^k` over 1M queries; bound coverage of real-target count.
- CMS: zero underestimates (with 10% deletes, skewed stream); overshoot-band exceedance <= e^-d; [low,high] coverage >= 1-e^-d minus slack.
- LogLog: m=256/n=20000 and m=64/n=8000; RMS <= 1.10 x 1.30/sqrt(m); |mean bias| < 0.25 sigma; coverage.
- Linear Counting: m=4096 at n=1000/4000/8000; RMS <= 1.10 x sqrt(m(e^t-t-1))/n; coverage.
- Reservoir: chi-square uniformity of inclusion by stream position; unbiased frequency scaling within 3%; frequency and distinct-count coverage.
- Exact: zero error under capacity with deletes.
- The 1.10 factor on RMS is sampling headroom (RMS over 1,000 trials has ~2.2% relative error). **Never loosen further without asking** (CLAUDE.md rule).
- Observed numbers (how close each test lands to theory) are not printed, so wide margins or accidental passes would go unnoticed.
