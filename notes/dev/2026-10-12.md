## M2 step 3: challenges and damage
Code is in `packages/engine/src/combat/`.

| File | Purpose |
| --- | --- |
| `damage.ts` | The three strike formulas: `frequencyStrike`, `countStrike`, `presenceStrike`. Pure arithmetic on a `DamageRules` object (the constants from `balance.json`). |
| `challenges.ts` | `issueChallenge` creates the question for a turn. `trueAnswer` and `gradeStrike` judge a strike against the live stream. |

Also added `outsideValue` in `enemies/stream.ts`: a value the enemy can never emit (the affine image of an index beyond the universe), used for never-inserted Presence decoys.

**Challenges**
- Frequency: names the heaviest live value (ties to the lowest). Returns null when nothing is live.
- Count: carries no data; the answer is the live distinct count.
- Presence: `T` distinct targets, shuffled. `T/2 − 1` to `T/2 + 1` are real, sampled from live values. Decoys are ghosts or outside values, equally likely while ghosts last. With fewer live values than wanted, the remainder are decoys.

**Grading**
- The challenge is not stored with its answer. The answer is recomputed from the `LiveSet` at strike time, which is valid because no events arrive between a challenge and its strike. A Presence target is real exactly when it is live.
- A strike of the wrong kind for the challenge throws a `RangeError`.

**Damage**
- Frequency: a force below the true count is blocked (costs `BLOCK_PENALTY`). Otherwise `BASE × (f/s)^OVERSHOOT_EXP`.
- Count: `BASE × (1 − |E − D| / (COUNT_TOL × D))`. An estimate on the edge of the band deals 0 and costs nothing. Beyond it costs `MISS_PENALTY`. With nothing live, only an estimate of 0 hits.
- Presence: `HIT_DAMAGE` per real target, `DECOY_PENALTY` per decoy. Targets are chosen by position, from 0, with no repeats.
- Damage is rounded to six decimals. Whole-number exponents use repeated multiplication, which gives the same result on every JavaScript engine.
- These interpretations are recorded in `SPEC.md`.

**Tests (35 new, plus 2 for outside values)**
- Damage: block boundary, full damage at the exact count, falloff, monotonic decrease past the count, non-integer exponent, rounding, symmetric Count tolerance, edge and miss behavior, nothing-live case, Presence hits and decoys, input validation.
- Challenges: Frequency naming and tie rule, Presence composition (distinct, real count 5 to 7 of 12, real values live, decoys not live), ghosts and outside values both appear, position does not reveal real targets, determinism, sparse and empty streams, true answers, grading, and wrong-kind rejection.

## M2 step 4: the fight state machine
Code is in `packages/engine/src/combat/`: `types.ts`, `internal.ts` (shared helpers), `fight.ts` (`createFight`, `step`), `view.ts` (`observe`, `groundTruth`, `legalActions`), `index.ts`.

**State.** `FightState` is plain data: the config, seed, phase, turn, Certainty, enemy HP, one structure snapshot per slot, the stream state, the live-set snapshot, the challenge generator position, the open challenge and the revealed weak point. It survives JSON unchanged. `step` returns a new state and never edits the one it was given: it copies the top level and replaces nested parts wholesale.

**Turn loop** (`step`)
- Deploy phase: `deploy` and `remove` change a slot. `endDeploy` ingests the burst into every deployed structure, then from turn 2 issues the challenge, which moves the fight to the strike phase.
- Strike phase: `strikeValue` or `strikeSubset` is graded against the live set. HP and Certainty change, then the enemy attacks and the next turn begins.
- A fight ends in a win (HP reaches 0), or a loss (Certainty reaches 0, or the turn limit passes after the enemy's attack, with the turn-limit penalty). Once over, `step` throws and `legalActions` is empty.
- Illegal actions throw `IllegalActionError`: wrong phase, bad slot, slot taken, structure not owned, Space over budget, a structure that cannot be built at that size, or a strike that does not fit the challenge. `step` and `legalActions` share the same deploy check, so every listed deploy is accepted.
- Interpretations of the spec (resize, attack on turn 1, ordering of win and loss, weak point rotation) are recorded in `SPEC.md`.

**Views**
- `observe(state)` returns exactly: turn, phase, Certainty, enemy HP, free Space and slots, trait levels, the weak point (null until revealed), the open challenge, and each deployed structure with its answer to that challenge. The true answers are never included.
- `groundTruth(state)` returns the real heaviest value, its count and the distinct count, for bots and tests.

**Reward.** Each step returns a reward from `config.rewards` (default: +1 for a win, -0.01 per turn, -0.005 per Certainty lost, -1 when the run is lost).

**Tests (22).** Starting state and exposed fields, deploy rules and refunds, illegal actions, `legalActions` all accepted by `step`, the turn loop and event order, the heaviest value named from turn 2, Bloom unable to answer Frequency, a late structure seeing nothing earlier, blocked and hit strikes with exact damage, a won fight, a lost fight with exact Certainty arithmetic (100 - 12 - 9 - 20 = 59), determinism, purity, and a JSON round trip that continues identically.
- Mutation checks: skipping the turn-limit penalty, letting `step` edit its input, issuing a challenge on turn 1, and showing the weak point early each fail tests.
- A survey of 300 seeds with the greedy script: 300 wins (56 on turn 2, 244 on turn 3), no blocked strikes, no errors. The test enemy is easy; balance is tuned in M3.

**Known limits**
- The fight config (enemy HP, attack, size, turn limit, turn-limit penalty, expected turns) is supplied by the caller; the values are not in `balance.json` yet.
- `Infinity` in a Linear Counting answer is not yet encoded for JSON. Answers appear in `observe()` only, not in state or events.
- `legalActions` offers one structure size per share of free Space and no knob choices.
