## Action loops (rules version 2)
- Question: which actions can repeat without using a turn? Answer, from reading `step` in `combat/fight.ts` and `run/run.ts`: in a fight `deploy` and `remove` (free; a removal refunds all Space, so the pair returns exactly to the earlier state); at a rest stop `enchant` (moving an enchantment between structures is free and reversible). `fuse` consumes inputs, `chooseReward` happens once, `endDeploy` and the strikes advance the fight.
- The 26 capped games of the M8 agent (replayed under version 1 from the M8 commit with the saved model): all end in a pure two-step cycle of `deploy X in slot N` and `remove slot N`, begun at step 23 to 79 after 1 to 6 fights won, 24 of 26 in the Elite or Boss (details in SPEC.md, "No action loops"). The state after the removal equals the state before the deploy, so a deterministic policy repeats it for ever. It is a policy fixed point, not a trap the agent could not leave: a stochastic policy would sometimes leave.
- Change: `FightRules.changesPerSlot` (balance `DEPLOY_CHANGES_PER_SLOT`, 2): a turn allows that many deploys and removals per slot; `FightState.changes` counts them, resets with the turn; `legalActions` then offers only `endDeploy`; `Observation.changesLeft`. `RunConfig.restEnchantLimit` (`REST_ENCHANT_LIMIT`, 6) and `RunState.restEnchants` for rest stops. `ENGINE_VERSION` 2; the five replays were re-recorded (same outcomes). Chose budgets over "cannot immediately undo": that would forbid correcting a mistake and would not stop a three-step cycle.
- Tests: `run/progress.test.ts` (a stalling adversary for 12 slot and turn-limit combinations is stopped within `turn limit x (cap + 2)` accepted actions and loses to the turn limit; a rest-stop adversary shuffles to the limit then leaves; 150 arbitrary mostly-refused sequences keep every invariant and end); `fight.test.ts` "changes in a turn"; `env.test.ts` plays the stalling policy through the learning environment (ends by itself, not truncated).
- Mutation checks: no cap (caught), removals not counted (caught), no reset at the next turn (survived until the unit test was added, then caught), rest limit not applied in the offers (caught; the first version of the test hung instead of failing, because it only counted accepted actions, so attempts are bounded now), rest count not increased (caught); removing the second guard in `enchant()` is equivalent, since the offers are already empty at the limit.
- Side effects: the sim's "dawdler" test bot (deploy and remove for ever, to test the stall detection) is now an illegal player, so the stall test uses a tiny step limit instead. Bots are unaffected: Greedy 44.0, Prober 29.0, Cautious 11.0 over 300 runs, as before. The M8 agent and its 267-action layout are not retrained, and under the new rules it could not reproduce its loops anyway.
- A mistake of mine worth recording: running mutation checks in a shell loop that is killed leaves the mutated file behind. A hung run (mutation 4) was killed mid-way and `run.ts` kept the mutation until I diffed it; the diff is the check to make.

- The test that mattered: the Oracle did not one-shot every Rank fight (a mean of 2.25 turns instead of 2 in the simulator's report test). Cause: on skewed streams a heavy value spans more of the ranks than `RANK_TOL`, so no value reaches within the tolerance of an armor set at an exact quantile, and the best possible strike deals nothing. - Design choice worth recording: copies are named by position (`targets` 0..K-1) so every Presence code path (parser, bots, learning environment, query screen) works for Likeness unchanged, apart from the places that tested `kind === "presence"`.
- **A design question I settled by measuring.** MinHash describes every value ever inserted, so ghosts pull a similarity in both directions (a copy that holds ghosts looks more alike, one that does not looks less). I tried taking the expected ghosts out of the union (as K-Minimum Values does) and the flags got no better, so it is not in. The surely-real bound carries the ghost allowance.
- Mutation checks, 22 on MinHash and the generator: 15 caught at once; 7 survived and each led to a test: the ghost bound (a case with repeated inserts, where the binomial is below the deletes), the unbiased `k - 1` and the lognormal level (the formulas checked exactly against the signature), the minimum-size edge and the exact threshold edge, the shuffle of the copies (real copies must not always come first), and the spread of the real band (the share of real copies above 0.9 must be at least 0.1). **One is equivalent:** removing the `Set` that deduplicates a copy's values in `signatureOf` changes nothing but speed, since a repeated value cannot change a minimum.
