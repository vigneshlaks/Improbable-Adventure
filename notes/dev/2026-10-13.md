## Notes on running the tests
The statistical tests are CPU- and memory-heavy and have a 60-second limit each. On a loaded or memory-starved machine a test can exceed that and fail with a timeout while the code is fine; the k=14 Bloom test is the most exposed. Rerun when the machine is idle, or pass `--testTimeout=` to raise the limit.

## M3 step 2: command parser and narrator
New package `packages/ui-core` (shared by the CLI now and the web UI later), plus `packages/content/narration.json`.

**Narration content** (`narration.json`, `content/src/narration.ts`)
- Templates for every kind of event, the enemy's tier and trait descriptions, and the usage and summary of each command.
- Templates use `{name}` variables. `EVENT_TEMPLATES` lists the variables each template may use, and loading fails if a template names any other, so a typo like `{slott}` is caught at startup.

**Parser** (`ui-core/src/parser.ts`): `parseCommand(input, { observation, loadout? })`
- Returns an engine action (with an optional note such as which structure `strike high` used), an information request (`status`, `query`, `help [topic]`), `quit`, `empty`, or an error message. It never throws.
- Context-aware: it reads the observation to find the first free slot, check free Space, check the knob range, know whether a Presence or numeric challenge is open, and work out `flagged` and `confirmed` targets from the structures' answers.
- Slots and targets are numbered from 1 for the player and converted to the engine's 0-based numbers. Command aliases: `ready`, `go`, `done`; `quit`, `exit`, `q`; `?` for help.
- Mistakes get an explanation, and a likely typo gets a suggestion (`blom` suggests `bloom`, `stike` suggests `strike`).

**Narrator and screens** (`narrator.ts`, `views.ts`)
- `narrateEvent` and `narrateEvents` turn events into lines. The first challenge also reveals the weak point; Presence challenges list their targets from 1.
- `describeEnemy` introduces the tier and lists each trait above Low.
- `renderStatus`, `renderQuery` (each structure's estimate, range and confidence, which Presence targets each flagged, and which are confirmed) and `renderHelp` (commands, structures, knobs).

**Tests (64 in ui-core: 39 for the parser, 25 for the narrator and screens; 5 for the narration content)**
- Every command, alias, error and edge case of the parser, using hand-built observations so the numbers are exact.
- Narration of every event kind, the enemy description, and the three screens.
- Three whole fights (a Presence, a Frequency and a Count enemy) played from typed commands through the parser, the engine and the narrator, checking no template variable is left unresolved.
- Mutation checks: an off-by-one in `remove`, a 0-based slot in the narration, counting one structure as "confirmed", and silently ignoring a missing template variable each fail tests. Two of these first slipped through, which exposed a gap (the test did not check that a singly flagged target was not marked confirmed); the test was strengthened.


## M3 step 3: the five bots
New package `packages/sim` (batch runs and reports follow in step 4).

**Engine change.** `groundTruth(state)` now also returns `answer`: the true answer to the open challenge (for Presence, which targets are real). The Oracle needs it. `observe()` still never includes it.

**Structure of a bot** (`sim/src/bots/`)
- `Bot { name, description, usesTruth, create() }`. `create()` makes a fresh player per fight, so a bot can remember things as it goes. A player is `(view, rng) => Action`.
- `BotView` carries the observation, the loadout, a lazy `legalActions()` and `truth`. The runner sets `truth` only for bots with `usesTruth`; a test checks every other bot gets null.
- `common.ts` holds the shared decisions: the structures that suit each weak point (LogLog or Linear Counting for Count depending on Variety), the likeliest weak points from the trait hints, which structures to have deployed, the next step towards that (deploy with an even share of free Space, remove an unwanted structure to make room, or end deploying), and how to read numeric and Presence answers.

**The bots** (interpretations recorded in `SPEC.md`)
- Random: uniform over `legalActions()`.
- Greedy: two likeliest weak points, one structure each, strikes on the estimate, re-targets when the weak point is revealed.
- Prober: Reservoir Sampling with 40 percent of the first turn's Space, then Greedy.
- Cautious: two structures per weak point, Presence confirmed targets only, Frequency at the upper bound.
- Oracle: deploys nothing, strikes exactly.

**Runner** (`runner.ts`): `playFight({ config, seed, bot, maxSteps?, keepEvents? })` returns a `FightRecord` with the outcome (won, lost, or stalled), the loss reason, turns, Certainty left, Certainty lost by cause (blocked strikes, decoys, Count misses, enemy attacks, turn-limit penalty), strike counts, and the structures deployed. An illegal action from a bot throws an error naming the bot.

**Tests (37).** Contract (only the Oracle sees the truth, no bot ever takes an illegal action across all tiers and weak points, replays are deterministic), then each bot's behavior: Greedy's first deploy for each trait, its Space split and its re-targeting; Prober's opener; Cautious striking only confirmed Presence targets and never being blocked on Frequency; the Oracle winning a Minion on turn 3 with 94 Certainty; Random winning less than Greedy and the Oracle. Mutation checks: Cautious accepting a single flag, the Oracle overshooting by one, bots ignoring the revealed weak point, and a 90 percent probe each fail tests.

## First look at balance
150 fights per row, seeds `survey-0` to `survey-149`. "Starting" is the spec's starting loadout (Exact Memory, Reservoir Sampling, Bloom Filter); "full" adds the other three structures. Tier numbers are placeholders.

| Loadout | Tier | Random | Greedy | Prober | Cautious | Oracle |
| --- | --- | --- | --- | --- | --- | --- |
| starting | Minion | 0.35 | 0.67 | 0.59 | 0.36 | 1.00 |
| starting | Elite | 0.09 | 0.41 | 0.17 | 0.03 | 1.00 |
| starting | Boss | 0.00 | 0.01 | 0.00 | 0.00 | 1.00 |
| full | Minion | 0.25 | 0.79 | 0.66 | 0.53 | 1.00 |
| full | Elite | 0.01 | 0.59 | 0.22 | 0.19 | 1.00 |
| full | Boss | 0.00 | 0.07 | 0.00 | 0.00 | 1.00 |

What it shows (win rates per fight; the spec's targets are for whole runs):
- The Oracle wins every fight in every tier, so every tier is beatable. It finishes a Minion in 3 turns, an Elite in about 5 and a Boss in about 10, with 21 Certainty to spare against a Boss.
- Greedy's Minion win rate (0.67 to 0.79) is near the spec's 55 to 70 percent target for Greedy, but Random wins 25 to 35 percent of Minion fights against a target of under 5 percent, so Minions are too easy for a bot that plays badly.
- Bosses are almost unbeatable without perfect answers (Greedy at most 0.07), so the Boss numbers are too harsh.
- Probing is not dominant: Prober does worse than Greedy in every row.
- Safe play is weak: Cautious loses mostly to the turn limit, because striking nothing when no target is confirmed wastes turns. It is viable on Minions with the full loadout (0.53) and little else.
- Wrong strikes are 18 to 64 percent of Greedy's strikes (target 10 to 30 percent), highest with the starting loadout, which has no Count-Min.
- No fight stalled.

These are findings for the M4 tuning pass; nothing was changed.


## M3 step 4: batch runs and reports
Code is in `packages/sim/src/`: `report.ts`, `format.ts`, `cli.ts`, `bin.ts`, `stats.ts`.

**Commands** (`pnpm sim ...`, run with `tsx`, added as a dev dependency)
- `sim fights --bot <name> [--n 1000] [--seed-base 1] [--tier minion|elite|boss] [--loadout starting|full] [--json]`
- `sim compare --bots a,b,c [same options]`: the same fights for every bot, side by side.
- `sim runs`: prints that whole runs need the run loop (Milestone 4) and exits with code 1. The spec lists it, but there is nothing to run yet.
- 500 fights take about 1.8 seconds, so the spec's 10,000 take about 35 seconds.

**The report** (`runFights`, `summarize`): outcomes (won, lost to the turn limit, lost to Certainty, stalled), win rate with a 95 percent Wilson interval, turns per fight, Certainty left, Certainty lost per fight by cause, strikes per fight and the share that were wrong, each structure's deploy rate and the win rate of those fights, and each structure's accuracy in play.

**Accuracy in play.** The runner (`playFight`) now compares every deployed structure's answer with the true answer at each strike and keeps a tally per kind (`FightRecord.accuracy`): answers given, how many held the truth in their stated range, the confidence they claimed, and the relative error of the estimate. The decisions are recorded in `SPEC.md`.

**Other changes**
- `@types/node` is installed for the command-line code. Because that makes Node globals visible everywhere, eslint now bans `process`, `console`, `Buffer`, timers and `require` in engine files, so the engine stays free of them. A test file with `console.log` in the engine fails lint.
- `parseArgs` and `main` are plain functions that return the text and exit code, so the whole command line is tested without starting a process.

**Tests (46 new in sim: 83 in total)**: the Wilson interval; `summarize` against four hand-made fights with checked numbers; `runFights` (determinism, seeds, loadouts, bad counts); the accuracy tally (an Exact Memory with room is always in range with zero error); the formatted text; and the command line (every command, option form and error).

## Findings from the accuracy report
- **Bloom Filter ranges are overconfident when the enemy deletes.** With no churn its Presence range held the truth 99.6 percent of the time (claimed 95). With medium churn that fell to 37 percent, and with high churn to 18 percent. A Bloom filter cannot see deletes, so deleted values stay flagged, and its range only accounts for hash collisions. This is the structure's intended weakness (the spec says so), but its stated confidence does not reflect it. Like LogLog on tiny streams, it is a range that is confidently wrong in exactly the situations the game is built around. Whether the displayed range should change is a design decision; the structures were not changed.
- Exact Memory's range always held the truth (it widens by the number of values it refused), but its estimate was off by about 66 percent on average with the starting Space, because 4,096 bits holds only 64 values.
