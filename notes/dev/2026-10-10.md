## Changes
- **Frequency challenge shape (decided).** The enemy names its heaviest live value `v`; `query` asks every capable structure about `v`. The player never sees the true count `f`. The engine recomputes `v` and `f` each turn from exact live counts, and ties go to the lowest value. Recorded in `SPEC.md`, Challenges section. The structures already take `{ kind: "frequency", value }`, so no structure code changed.
- **`binomialUpper` is stable for large trial counts.** The old loop started from `(1 − p)^n`, which rounds to zero for large `n·p`, so it returned `n`. It now tracks log-probabilities. Test: `binomialUpper(100000, 0.5, 0.95)` is about 50,260.
- **Two constants moved into `balance.json`:** `CMS_DEFAULT_DEPTH` (4) and `LOGLOG_ERROR_COEFFICIENT` (1.3). `StructureConstants` gained `cmsDefaultDepth` and `logLogErrorCoefficient`, and the exported `DEFAULT_CMS_DEPTH` and `LOGLOG_ERROR_COEFFICIENT` are gone.
- **Drift check.** `content/src/balance.test.ts` asserts the engine's stand-in `TEST_CONSTANTS` equals `structureConstants()`. It imports the engine's test helper by relative path, which is deliberate: it is a test, and the engine's own import rules do not cover it.
- **Comment pass.** Doc comments now state what a thing is and its key behavior, and name the technique so it can be looked up. Derivations moved out of the code.

**Acceptance:** a scripted fight replays identically from its seed, and its state round-trips through JSON.

**In scope:** stream generator (Variety, Skew, Churn, Growth, Drift), Presence/Frequency/Count challenges, damage rules, single-fight loop (`step`, `legalActions`, `observe`).
**Out of scope:** Cunning, Likeness and Rank (M9); rewards, rest stops and fusions (M4).

Steps, each ending with passing tests and lint:
1. **Structure snapshots.** `snapshot()` and `restore()` using only numbers, strings and arrays. Test: snapshot, restore, feed both the same events, and answers must match.
2. **Stream generator and ground truth.**
   - Draw values by Zipf rank and map ranks to values through a seeded permutation.
   - Burst size per turn is `Size / EXPECTED_TURNS × growth^t`.
   - Churn deletes only currently live values.
   - Drift reshuffles part of the rank-to-value mapping every few turns.
   - A separate exact tracker records live counts, the top value `v` and count `f`, the distinct live count `D`, and the deleted ("ghost") values.
   - Proposed: an explicit permutation and a table-based Zipf sampler behind a small interface (`nextEvent()`, `truth()`). A keyed bijection with O(1) memory is a later optimization if generation proves slow or memory-heavy at the largest Variety level (2^22 values).
   - Tests: Zipf shape (chi-square), delete share, growth.
3. **Challenges and damage.**
   - Presence: `T` targets, about half real; decoys are never-inserted values and ghosts.
   - Frequency: as decided above.
   - Count: the live distinct count `D`.
   - Damage: the three formulas from `SPEC.md` using `balance.json` constants.
4. **Fight state machine.**
   - Phases: deploy, ingest, challenge, query, strike, enemy attack.
   - Space and slot accounting, copy-on-write state, and events for the narrator.
   - The weak point stays hidden until the first challenge, and challenges start on turn 2.
   - Turn limit and its penalty.
5. **Golden-fight test, written first.** Same seed and actions give an identical event log; `step` never mutates its input; state survives a JSON round-trip and continues identically.

**Config:** add placeholder values to `balance.json` for `EXPECTED_TURNS`, per-tier HP, attack, size and turn limit, and the turn-limit penalty. The spec gives none; the M3 simulator tunes them. Level tables go in `traits.json`, and the engine receives them as plain config objects.

## Bloom k=14 gap (explained, accepted)
**Decision (2026-10-10):** accept the gap and document it. The hashing, `currentFalsePositiveRate()` and the test's tolerance are unchanged.

**Measurement.** Throwaway script outside the repo, using the repo's `murmur3.ts` and `doubleHash.ts`. n=400, k=14, 1,500 filters per row, 20,000 fresh random queries per filter (about 3×10^7 queries per row).

| Setup | observed / textbook | ±1 SE | distinct positions per value |
| --- | --- | --- | --- |
| m=8000, repo hashing | 1.146 | 0.021 | 13.978 |
| m=8192, repo hashing | 1.163 | 0.023 | 13.985 |
| m=8192, h2 forced odd | 1.282 | 0.022 | 13.983 |
| m=8192, ideal random positions | 0.997 | 0.025 | 13.989 |
| m=8000, ideal random positions | 1.019 | 0.022 | 13.988 |

Observed / mean(fill^k) matched observed / textbook within 1% in every row, and measured fill matched 1 − e^(−kn/m) to 4 decimals.

**Ruled out.**
- Sampling noise: the gap is about 7 SE.
- The textbook formula's known underestimate (Bose et al. 2008): ideal random positions match it at this size.
- Power-of-two m: m=8000 shows the same gap.
- Self-collisions among a value's k positions: same rate as ideal positions.

**Cause.** In enhanced double hashing, all k positions are a function of (h1 mod m, h2 mod m). A query that shares that pair with any inserted value gets identical positions and is a certain false positive. That happens with probability about n/m^2 = 400/8192^2 ≈ 6×10^−6, about 11% of the textbook rate 5.3×10^−5. Near-matches supply the rest; for example, the same h2 with h1 shifted by one h2 step shares 13 of 14 positions. The effect is additive, so it is only visible when the base rate is tiny (large k, low fill). At about 1% false positives it is negligible. Forcing h2 odd halves the h2 space, roughly doubles the excess, and matches the 1.28 row.

**Game impact.** `currentFalsePositiveRate()` = fill^k reads about 15% low here, so Bloom's low bound is very slightly optimistic. With 12 Presence targets and p ≈ 6×10^−5, `binomialUpper` returns 0 either way, so no answer changes today.

**If revisited.**
- (a) Use p ≈ fill^k + n/m^2 in the rate and in the test reference. This keeps replays intact, but changing the test bound needs sign-off, since test bounds are not loosened without it.
- (b) Use k independent Murmur3 hashes for Bloom. This costs k hashes per value and changes every position, so it breaks replays.
- Recheck if Presence challenges grow well beyond 12 targets or very low-error filters become common.
