## Structure snapshots
Every structure can be saved as plain data and rebuilt exactly. The fight state needs this: it must survive `JSON.stringify` and `JSON.parse`, and typed arrays and Maps do not.

- `Structure.snapshot()` returns a `StructureSnapshot`: the kind, the options it was built with (`spaceBits`, optional `knob` and `hashSeed`), and a `state` object of numbers, strings and arrays.
- `restoreStructure(snapshot, constants)` rebuilds a live structure. Each class has a `fromSnapshot` that constructs an empty structure of the same shape and then loads the contents.
- Optional fields are left out when unset, so a snapshot is unchanged by a JSON round trip.

| Structure | `state` holds |
| --- | --- |
| Exact Memory | `entries` (flat list of value, count pairs in insertion order), `refused` |
| Reservoir Sampling | `sample`, `seen`, `rng` (the random generator's position) |
| Bloom Filter | `bits` (32-bit words), `setBits`, `insertCount` |
| Count-Min Sketch | `counters`, `total` |
| LogLog | `registers` |
| Linear Counting | `bits` (bytes), `zeros` |

Details worth knowing:
- Reservoir Sampling saves its random generator position. Without it, a restored sample makes different random choices than the original. Removing that line makes three tests fail.
- Restoring validates its input. A missing key, a non-number, a negative or fractional count, an array of the wrong length, a kind that does not match the state, or an unknown kind all throw a `RangeError`.
- Snapshots are copies. Later events on the live structure do not change an earlier snapshot.
- Snapshots contain no answers, so `Infinity` (Linear Counting's saturated upper bound) is not in them. Its JSON encoding is still needed for answers and events.

Tests (`structures/snapshot.test.ts`, 46 tests): for each structure, a JSON round trip leaves the snapshot unchanged, a restored structure has the same parameters, space and answers, it keeps behaving identically as 600 more events arrive, an empty structure restores, a snapshot is a copy, and malformed input is rejected. Extra checks cover array length, negative and fractional entries, an unknown kind, and merging a restored Bloom filter with its original.

## M2 step 2: stream generator and ground truth
Code is in `packages/engine/src/enemies/`.

| File | Purpose |
| --- | --- |
| `permutation.ts` | `makePermutation(n, key)`: a seeded permutation of `0..n-1` with no stored table (a Feistel network with cycle walking). |
| `zipf.ts` | `createZipfSampler(n, s)`: draws a rank in `1..n` in O(1) time with no table (rejection-inversion sampling). `s = 0` is uniform. |
| `liveSet.ts` | `LiveSet`: the exact record of what is live, how often, and which values are ghosts. Challenges are graded against this. |
| `stream.ts` | `resolveStreamParams`, `createStream`, `nextBurst`, `burstSize`, `rankToValue`. Turns trait levels into numbers and generates each turn's events. |

**Why a keyed permutation and not a stored shuffle.** The fight state must be JSON. A shuffled table for the largest Variety level (2^22 values) would add tens of megabytes to every saved state. The mapping is instead rebuilt from the seed and the number of drift events, so the stream state is `{ seed, turn, driftEpochs, rng }` (a few hundred bytes).

**Traits as generated**
- Variety: the universe size (256, 16,384 or 4,194,304 values). Ranks map to distinct uint32 values through the permutation and an affine map with an odd multiplier.
- Skew: Zipf exponent 0, 0.8 or 1.2.
- Churn: each event is a delete with the stated probability, removing one live unit chosen uniformly at random. With nothing live it becomes an insert.
- Growth: burst size is `baseBurst × growth^(turn − 1)`, built by repeated multiplication so every JavaScript engine gives the same result, then rounded.
- Drift: before the burst of every turn divisible by `everyTurns`, the top `fraction` of ranks is reshuffled. Lower ranks keep their values.

The interpretations of the spec (growth exponent, drift schedule, delete choice) are recorded in `SPEC.md`.

**`LiveSet`**
- Stores one entry per live unit, so a random delete is O(1).
- `mode()` is the heaviest live value, ties to the lowest value. This is the value the Frequency challenge names.
- Fully deleted values become ghosts; inserting one again removes it from the ghosts.
- Snapshots round-trip through JSON and reject malformed input.

**Tests (49)**
- The permutation is a bijection for sizes from 1 to 65,537, depends on its key, and works at 2^22.
- Zipf matches the exact distribution by chi-square for `s` of 0, 0.8, 1 and 1.2; at 2^22 ranks the rank-1 share is within four standard deviations of theory.
- The stream respects each trait: burst sizes, universe size, near-flat versus concentrated popularity (rank-1 share matches the Zipf share), delete share, only live values deleted, ghosts present, and the drift schedule.
- Drift keeps the mapping one-to-one at every epoch and reshuffles only the top block among its own values.
- Replays are identical from the same seed, `nextBurst` never mutates its input, and a saved state resumes identically.
- Mutation check: skewing the sampler's exponent by 0.1 fails four tests.

**Known limits**
- `Math.exp`, `Math.log` and `Math.pow` appear in the Zipf sampler. They can differ in the last digit between JavaScript engines; a draw would change only if a uniform sample landed within about 1e-16 of a boundary.
- Fixing the ghosts test needed a larger universe: with 256 values and 5,000 events every value has about 15 live copies, so none is ever fully deleted.
